# ADR-0003: AprilProfile — метамодель, версии, authority, события и доступ

- **Дата:** 2026-04-17
- **Статус:** принято
- **Контекст:** Нужны единые правила **идентичности**, **версионирования**, **разрешения конфликтов между источниками**, **событий** и **доступа к чувствительным атрибутам**, чтобы реализация и интеграции были предсказуемыми и объяснимыми для compliance.
- **Решение:**
  1. **Идентичность:** стабильный **`entity_id`** (UUID) per профиль; внешние ключи — в маппинге `(tenant_id, source_system, external_id)`; merge дубликатов — явная операция с аудитом.
  2. **Метамодель:** тип сущности с **версионируемой схемой**; тело профиля — документ по схеме; домены в **namespace** (`hr`, `security`, …).
  3. **Версии:** append-only; **откат** только новой версией; история не переписывается.
  4. **Authority:** конфликты разрешаются **по полю / namespace** с детерминированными правилами и опциональным ручным разрешением.
  5. **События:** минимум `tenant_id`, `entity_id`, `entity_type`, `profile_version`, `occurred_at`, `event_id`; доставка at-least-once, идемпотентность потребителей; порядок по сущности — по `profile_version`.
  6. **Доступ:** Keycloak — RBAC экосистемы; Profile — **ABAC** по меткам полей; чувствительные сегменты не отдаются без права.
  7. **Персональные данные:** по умолчанию псевдонимизация и ограничение выдачи при сохранении аудита; полное стирание истории — исключение по процедуре.
  8. **Синхронизация:** идемпотентные батчи с checkpoint; поиск v1 — в PostgreSQL; отдельный поисковый слой — при необходимости.
- **Последствия:** Реализация merge-правил и схем событий должна быть тестируема; схемы типов требуют процесса публикации (ревью, draft/published). Детали — в [Дизайн модуля AprilProfile](/docs/design-april-profile) (`docs/DESIGN_AprilProfile.md`).
