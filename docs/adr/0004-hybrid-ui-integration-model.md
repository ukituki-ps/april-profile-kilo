# ADR-0004: Гибридная модель интеграции UI (Host-driven, Widget-driven, API/BFF-first)

- **Дата:** 2026-04-20
- **Статус:** принято
- **Контекст:** В экосистеме April одновременно нужны полноэкранные оркестрационные экраны в **AprilHub** (host), переиспользуемые доменные блоки в npm-пакетах **`@april/*-ui`**, и переходные сценарии, где интеграция идёт через **API/BFF** без развитого слоя виджетов. Без явной модели и governance легко смешать ответственность host/widget, продублировать навигацию, разъехаться по версиям DS и нарушить мультитенантность/ABAC.

- **Решение:** Зафиксировать **гибридную** политику: допускаются три равноправных варианта интеграции UI — **Host-driven**, **Widget-driven**, **API/BFF-first** — с едиными контрактами [HostContext / props / events v1](/docs/widget-contracts), политикой [версионирования и совместимости](/docs/versioning-and-compatibility), [матрицей решений](/docs/decision-matrix-ui-integration) и обязательными правилами владения навигацией (**host** владеет маршрутизацией; **widget** испускает intent-события, не подменяя глобальный роутер).

  1. **Host-driven:** экран целиком в приложении host; подходит для уникальных админских потоков и сложной IA.
  2. **Widget-driven:** переиспользуемые React-компоненты из `@april/*-ui` (доменная логика отображения и вызовов API в границах пакета; без доменной логики в DS).
  3. **API/BFF-first:** потребление данных и действий через BFF/API без обязательного слоя виджетов (например ранний этап или тонкий клиент).

- **Последствия:**
  - **Плюсы:** Предсказуемость для команд сервисов и Hub; возможность эволюции экрана за счёт смены режима (например API-first → widget) без смены доменных контрактов API.
  - **Минусы / trade-offs:** Нужна дисциплина semver, согласование major с consumer (Hub), процесс deprecation. Три режима увеличивают объём документации и ревью «куда положить код».
  - **Риски:** Дублирование UI между host и виджетами; рассинхрон версий `@april/ui` и `@april/*-ui`; обход BFF и утечка `tenant_id`. Митигация — чеклисты релиза/интеграции, матрица совместимости, telemetry contract ([руководство по observability](/docs/widget-observability-guide)).

## Варианты, которые рассматривались

| Вариант | Суть | Почему не выбран как единственный |
|--------|------|-----------------------------------|
| Только host-экраны | Вся UI в Hub, без общих npm-виджетов | Дублирование между сервисами (Profile, NFlow, OrgFlow), медленная эволюция общих блоков. |
| Только виджеты | Все продуктовые экраны только через `@april/*-ui` | Нереалистично для уникальных админок и переходного периода без готовых пакетов. |
| Только API/BFF | UI минимален, всё в данных | Не покрывает богатые сценарии и единый UX/DS без повторной реализации в каждом host. |

**Вывод:** принята **гибридная** модель с явным выбором режима по матрице и фиксацией контрактов.

## Migration path

1. Зафиксировать текущие экраны как Host-driven или API/BFF-first.
2. Для повторяющихся блоков — выделить границы виджета; шаблоны спецификаций в репозитории: `docs/templates/WIDGET_SPEC_TEMPLATE.md`, `docs/templates/HOST_INTEGRATION_SPEC_TEMPLATE.md`.
3. Версионировать пакеты по [политике версионирования](/docs/versioning-and-compatibility); обновлять Hub в одном PR с bump зависимостей при major.

## Rollback / exit strategy

- Откат на предыдущую **minor/patch** версию виджета и host lockfile без смены API сервисов.
- При провале виджета: временно заменить встраивание на **host-only** экран или тонкий **API/BFF** клиент с теми же бэкенд-контрактами; навигация остаётся на host.
- Устаревший режим документируется в ADR как «устарело» при смене стратегии доставки UI (например переход на Module Federation) — контракты props/events сохраняются.
