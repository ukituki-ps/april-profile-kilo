# ADR-0005: Ревизии типа сущности и привязка `entity` к опубликованной схеме

- **Дата:** 2026-04-30
- **Статус:** принято
- **Контекст:** Эволюция JSON Schema (или эквивалента) для типа сущности **почти всегда обратно несовместима**. Нельзя автоматически «переезжать» всем существующим `entity` на новую схему без явного шага: иначе ломается интерпретация уже сохранённых документов профиля, нарушается воспроизводимость аудита и невозможно безопасно согласовать интеграции. Требуется модель, где **контракт схемы версионируется независимым потоком ревизий**, а каждая сущность **явно привязана** к конкретной опубликованной ревизии до момента управляемого апгрейда.
- **Решение:**
  1. Ввести **семейство типа** (логический тип в пределах `tenant_id`), стабильно идентифицируемое парой **`namespace` + `code`** (как человекочитаемый ключ; допускается дублирующий UUID `family_id` в хранилище для ссылочной стабильности — по усмотрению реализации, см. задачи репозитория).
  2. Ввести **неизменяемые ревизии схемы** (`revision_no` монотонно внутри семейства, начиная с 1): каждая ревизия после публикации — **immutable снимок** схемы (`published_schema_json`-аналог на уровне строки ревизии). Черновик редактируется до публикации; **повторная публикация обязательна** для выпуска новой ревизии.
  3. Каждая строка **`entities`** хранит ссылку на **ревизию схемы**, по которой документ профиля должен интерпретироваться и валидироваться (**bound revision**). Новые сущности по умолчанию создаются с привязкой к **последней опубликованной** ревизии соответствующего семейства.
  4. Переход сущности на более новую ревизию — **явная доменная операция** «upgrade binding»: успех подразумевает либо уже совместимый документ против целевой схемы, либо успешную **трансформацию** (если позже вводится слой миграций документа); при любом успешном изменении контрактно значимых данных профиля — **новая строка в `profile_versions`** (append-only), согласованная с ADR-0003.
  5. События и интеграции: в полезную нагрузку событий изменения профиля желательно включать достаточно данных для потребителей, чтобы понимать **ревизию типа**, применимую к документу (как минимум на уровне API/контракта событий — см. задачи на бэкенд); без ломания идемпотентности и порядков по ADR-0003.
  6. UI для администрирования каталога типов и апгрейдов — **виджет** с контрактом embed (HostContext), **строго через дизайн-систему** (`@april/ui`, Mantine в рамках принятого стека); см. карточку [`docs/widgets/profile/entity-types-widget.md`](../widgets/profile/entity-types-widget.md).
- **Последствия:** Потребуется миграция от текущей модели таблицы `entity_types` (draft/published в одной строке) к целевой (семейство + таблица ревизий + привязка `entities`). Потребуется расширение OpenAPI и SDK. Это **не** «MVP»: реализация должна покрыть CRUD семейства, жизненный цикл черновика/ревизий, bind на `entities`, операции upgrade и интеграционные тесты.
