# ADR-0002: AprilProfile — назначение, границы с экосистемой и мультитенантность

- **Дата:** 2026-04-17
- **Статус:** принято
- **Контекст:** Нужно зафиксировать, **что** разрабатывается в репозитории april-profile: универсальное хранилище профилей, а не узкий HR-справочник; также нужна явная политика **нескольких организаций** в одной инсталляции и разграничение с AprilOrgFlow, EDC и IAM.
- **Решение:**
  1. **Продукт:** AprilProfile — централизованное версионируемое хранилище **профилей сущностей** расширяемых типов (персонал, подразделения, должности, клиенты, техника, проекты, договоры и др.). HR и Security — примеры доменных атрибутов, не ограничение модели.
  2. **AprilOrgFlow** владеет **графом** организации (иерархии, матричные связи). AprilProfile владеет **атрибутивным профилем** и версиями; ссылается на идентификаторы OrgFlow без дублирования графа.
  3. **AprilEDC** и прочие коннекторы не создают произвольные типы в мастер-данных: только **whitelist** типов и полей, согласованный с Profile.
  4. **Мультитенантность:** обязательный **`tenant_id`** на сущностях, версиях, маппингах и событиях; изоляция в API из **доверенного** контекста аутентификации (Keycloak / BFF); кросс-тенант по умолчанию запрещён.
- **Последствия:** Все API и схемы БД проектируются с учётом tenant; интеграции с OrgFlow требуют согласованных идентификаторов и валидации tenant. Документ дизайна: [Дизайн модуля AprilProfile](/docs/design-april-profile) (в репозитории: `docs/DESIGN_AprilProfile.md`).
