## 1. Цели

- **Единый визуальный язык** с остальной платформой: `@april/tokens`, `@april/ui`, Mantine (см. `docs/guides/DESIGN_SYSTEM.md`).
- **Предсказуемая интеграция с AprilHub**: встроенные сценарии (списки, мастер-потоки) и полноэкранные админские задачи не расходятся по UX и правам доступа.
- **Мультитенантность и ABAC**: `tenant_id` и чувствительные поля не «протекают» из UI; поведение согласовано с ADR-0002/0003 и бэкендом.
- **Минимум дублирования**: бизнес-логика обращения к API и правила отображения полей — в переиспользуемых модулях, а не копипаста между админкой и Hub.
- **Governance гибрида**: три режима интеграции (§2) с формальными контрактами и матрицей решений, чтобы масштабирование не превратилось в хаос.

## 2. Три модели интеграции UI

Термины зафиксированы одинаково в документации и ADR-0004: **Host-driven**, **Widget-driven**, **API/BFF-first**. Подробная матрица выбора — [`DECISION_MATRIX_UI_INTEGRATION.md`](./DECISION_MATRIX_UI_INTEGRATION.md).

### 2.1 Host-driven

**Суть:** классический экран целиком в приложении **host** (AprilHub или согласованный shell).

- **Когда:** уникальные оркестрационные/админские потоки, сложная информационная архитектура, сценарии с низким повторным использованием между микросервисами.
- **Anti-patterns:** копирование больших блоков между командами без выделения примитивов DS или виджета; дублирование вызовов API без общего клиента.
- **Риски / стоимость:** низкая на старте; растущий долг при копипасте и расхождении UX.

### 2.2 Widget-driven

**Суть:** переиспользуемые React-блоки в npm-пакетах **`@april/*-ui`** (например профиль сущности), потребляемые host.

- **Когда:** один и тот же UX нужен в нескольких местах или репозиториях (AprilProfile, NFlow, OrgFlow и т.д.).
- **Anti-patterns:** доменная логика в **Design System**; виджет монтирует собственный `BrowserRouter` или неявно управляет глобальной навигацией; обход BFF.
- **Риски / стоимость:** процесс semver, согласование major с Hub, поддержка changelog и интеграционных спецификаций (см. [`VERSIONING_AND_COMPATIBILITY.md`](./VERSIONING_AND_COMPATIBILITY.md)).

### 2.3 API/BFF-first

**Суть:** интеграция через **API и BFF** без развитого слоя виджетов — тонкий клиент, автогенерированные формы, переходный режим.

- **Когда:** ранний этап продукта, нет готового `@april/*-ui`, или достаточно данных без богатого UI.
- **Anti-patterns:** постоянное «залипание» на тонком клиенте там, где уже есть стабильный UX и дублирование экранов между сервисами.
- **Риски / стоимость:** быстрый старт; возможный разъезд UX и дублирование вызовов API на стороне host при росте требований.

## 3. Границы ответственности: DS, domain widgets, host

| Слой | Репозиторий / пакет | Ответственность |
|------|---------------------|-----------------|
| **Design System** | `@april/tokens`, `@april/ui` | Визуальные примитивы, тема, a11y; **без** доменной логики AprilProfile/NFlow и без знания tenant/API. |
| **Domain widgets** | `@april/*-ui` (например `@april/profile-ui`) | Доменный UI и вызовы API в границах сценария; соблюдение [`WIDGET_CONTRACTS.md`](./WIDGET_CONTRACTS.md). |
| **Host pages** | AprilHub (и при необходимости shell сервиса) | Маршрутизация, layout, сценарный state, OIDC, передача `HostContext`, обработка событий виджета. |

---

## 3.1 Правило DS-first для реализации UI

- Для новых экранов и виджетов приоритет — готовые компоненты/паттерны `@april/ui` (DisignApril).
- Если паттерн покрыт частично, предпочтительна обёртка/расширение поверх DS-компонента, а не самостоятельная реализация с нуля.
- Кастомный UI без DS-компонента допустим только как исключение с явной фиксацией причин и trade-off в task/report артефактах.

- **HostContext v1**, **Widget Props/Events v1** — единая формализация в [`WIDGET_CONTRACTS.md`](./WIDGET_CONTRACTS.md): минимум `tenant`, `auth`, `theme`, `locale`, `telemetry.requestId`; события `onSaveSuccess`, `onAction`, `onError` и навигационные **intent** (не прямой `navigate` из виджета).

## 5. Композиция в AprilHub

Host собирает страницу из layout, провайдеров (тема, OIDC) и **вставок** domain widgets. Виджет не дублирует корневые провайдеры и не владеет глобальным URL-пространством: он эмитит события, host решает, куда вести пользователя. Паттерн «админка vs встраиваемый блок» из §6–7 остаётся; выбор между host-only экраном и виджетом определяется §2 и матрицей.

## 6. Гибрид в продукте: две зоны UX

### 6.1 Админка — отдельное URL-пространство

**Назначение:** операторы данных, администраторы домена, задачи со **сложной навигацией** и **длинными формами**: каталог типов сущностей и версий схем, аудит, маппинг полей, статусы синхронизации с источниками, разбор конфликтов (при ручном merge).

**Как выглядит:** выделенный префикс маршрутов, например `/admin/profile/...` (внутри приложения AprilHub или отдельного shell — решает команда Hub; принцип один). Отдельная IA (меню, хлебные крошки), при необходимости отдельный layout.

**Плюсы:** закладки, явное разделение «операционная работа» vs «встроенный сценарий»; проще навесить **route guard** по ролям Keycloak («только админ-раздел»).

Обычно это **Host-driven**; отдельные блоки могут быть вынесены в `@april/*-ui` при повторном использовании.

### 6.2 Встраиваемые компоненты — внутри AprilHub

**Назначение:** сценарии **в контексте** других экранов: просмотр/редактирование карточки профиля в цепочке «список подразделения → карточка → сохранить → следующий», виджеты, врезки.

**Как выглядит:** npm-пакет (или модуль монорепо), экспортирующий React-компоненты, например:

- `<EntityProfileView entityId={...} entityType={...} onSaveSuccess={...} />`
- при необходимости облегчённые обёртки под конкретные сущности.

**Контракт с Hub:** пропсы и колбэки (см. §8 и `WIDGET_CONTRACTS.md`). Hub владеет **очередью просмотра** и **маршрутом**; компонент не дублирует список подразделения, если это не оговорено явно.

### 6.3 Почему не только микрофронты (Module Federation)

**По умолчанию** для встраиваемых сценариев предпочтителен **импорт компонентов/пакетов**: один контекст React Router, одна тема, проще типизация и CI.

**Module Federation** (или аналог) рассматривается, когда появляется жёсткое требование **независимого деплоя UI** без публикации npm и пересборки Hub. Тогда контракты из §4 и §8 сохраняются; меняется только механизм доставки бандла (см. §10).

## 7. Разделение по репозиториям (ориентир)

| Уровень | Где живёт | Примечание |
|--------|-----------|------------|
| **Каркас SPA, OIDC, общий layout** | AprilHub (или согласованный shell) | Единая точка входа для пользователя. |
| **Пакет UI + хуки API профилей** | Публикуется из репозитория AprilProfile (`frontend/` → артефакт `@april/profile-ui` / scoped npm) или общий монорепо по договорённости | Версионирование semver; breaking — мажор. |
| **OpenAPI → клиент** | Генерация из `openapi/openapi.yaml` в consumer или в shared пакете `@april/profile-api-client` | Один источник правды для контрактов. |

Точные имена пакетов и монорепо фиксируются при первом релизе клиентских библиотек.

## 8. Контракт встраиваемого профиля с AprilHub

### 8.1 Идентификация и навигация

- Текущая сущность отражается в **URL** (например `.../employees/:employeeId`), чтобы поддерживать обновление страницы и обмен ссылками.
- **Hub** хранит упорядоченный список ID в контексте сценария (например сотрудники подразделения) и передаёт в компонент:
  - идентификаторы и при необходимости `tenantId` из доверенного контекста (токен / BFF), а не произвольный ввод.

### 8.2 Колбэки после успешного сохранения и события

- Компонент профиля после **успешного** ответа API вызывает переданный с хоста колбэк, например `onSaveSuccess?: () => void`.
- **Hub** в реализации колбэка переводит на **следующий** ID из своего списка (`navigate` тем же роутером).

Так Hub «узнаёт», что нужно сменить карточку: сигнал явный, без скрытых глобальных событий (event bus допустим как альтернатива, но хуже для трассировки). Полный набор событий и intent — [`WIDGET_CONTRACTS.md`](./WIDGET_CONTRACTS.md).

### 8.3 Тема и провайдеры

- **Один** провайдер темы Mantine / `AprilProviders` на корне приложения **хоста**.
- Встраиваемый компонент **не** монтирует второй `BrowserRouter` и не дублирует корневой `MantineProvider`, если оболочка уже на Hub.

## 9. Админ-зона: маршруты и доступ

- Маршруты `/admin/...` (или согласованный префикс) защищены **проверкой ролей/claims Keycloak** (и при необходимости ABAC на уровне API).
- Тот же OIDC-клиент и сессия, что и у Hub; отдельный «логин в админку» без необходимости не вводить.
- Длинные таблицы и фильтры не обязаны дублировать компоненты встраиваемого профиля: общие **примитивы** (таблица, фильтры) — из `@april/ui` / общих пакетов April.

### 9.1 Контракт Hub BFF -> AprilProfile (dev-first)

Для фазы 4.2 фиксируем режим, который использует AprilHub BFF:

- **Публичный путь в Hub:** `/admin/profile/api/v1/...`.
- **Внутренний путь сервиса:** AprilProfile обслуживает API как `/api/v1/...`; BFF/reverse proxy снимает префикс `/admin/profile` перед отправкой в сервис.
- **Авторизация:** `Authorization: Bearer <access_token>` передаётся в сервис без подмены; tenant извлекается backend-ом только из trusted JWT claim (`tenant_id` по умолчанию).
- **Trusted proxy headers:** допускаются `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Prefix`; они используются только как контекст прокси и не являются источником tenant или RBAC-решений.
- **Анти-паттерн (запрещено):** принимать tenant из query (`?tenant_id=`), body или произвольных браузерных заголовков.
- **CORS:** для сценария через BFF целевой режим same-origin (Hub frontend -> Hub BFF -> Profile API). Расширение CORS под прямые браузерные вызовы к Profile делается только по отдельному ADR.

Минимальный smoke до готовности Hub выполняется через локальный nginx reverse proxy по гайду `docs/guides/PROFILE_BFF_DEV_SMOKE.md`: запросы к `/admin/profile/api/v1/auth/whoami` и доменным endpoint-ам должны проксироваться в AprilProfile без изменения JWT-контекста.

## 10. Module Federation (опционально)

Если remote подключается к Hub:

- **Shared:** `react`, `react-dom` как singleton; по договорённости — `react-router`, `@mantine/core`, чтобы не было двух деревьев и двух тем.
- Remote экспортирует **компонент с теми же пропсами**, что и пакетный вариант (`employeeId`, `onSaveSuccess`, …).
- Роутер остаётся на **хосте**; remote не определяет корневую навигацию экосистемы.

Подробнее о различии пакета и MF — в обсуждении команды; фиксация — при появлении отдельного ADR на доставку UI (контракты host/widget сохраняются).

## 11. На что смотреть, чтобы гибрид не ломался (чеклист)

1. **Дизайн-система:** все зоны (админка и встраиваемые блоки) используют **одни** `@april/tokens` / `@april/ui`; версии согласованы с Hub.
2. **Аутентификация и tenant:** токен и `tenant_id` только из **доверенного** контекста (Keycloak / BFF); UI не подставляет tenant из недоверенных полей формы.
3. **Дублирование логики:** запросы к AprilProfile API — через **общий слой** (сгенерированный клиент, хуки), а не отдельные копии `fetch` в админке и в Hub.
4. **Два Router / два React:** запрещено для встраиваемого режима; для MF — жёсткий `shared` и отсутствие второго корня провайдеров в remote.
5. **Права на поля:** сегменты `security`, `PII` и т.д. — поведение как в ADR-0003; фронт **маскирует** недоступное и не рассчитывает на «скрытие только в DOM».
6. **Совместимость версий:** semver, матрица host × widget, процесс deprecation — [`VERSIONING_AND_COMPATIBILITY.md`](./VERSIONING_AND_COMPATIBILITY.md).
7. **Тестирование:** критичные потоки (доступ к админ-маршруту, сохранение профиля, колбэк «следующий») — по [`TESTING_STRATEGY.md`](./TESTING_STRATEGY.md) (в т.ч. e2e при появлении стабильного API).
8. **Наблюдаемость:** `requestId` и error boundary — [`WIDGET_OBSERVABILITY_GUIDE.md`](./WIDGET_OBSERVABILITY_GUIDE.md); релиз/интеграция — [`WIDGET_RELEASE_CHECKLIST.md`](./WIDGET_RELEASE_CHECKLIST.md), [`WIDGET_INTEGRATION_CHECKLIST.md`](./WIDGET_INTEGRATION_CHECKLIST.md).

## 12. Каркас в этом репозитории

Каталог **`frontend/`** — Vite + React + Mantine + submodule DisignApril; предназначен для развития UI и последующей упаковки в библиотеку или артефакт, потребляемый Hub. До появления отдельного пайплайна публикации пакета достаточно согласовать с командой Hub **имя пакета и поток версий**.
