# Паттерн виджета: каталог + детальная карточка (master–detail)

Обобщённая логика встраиваемого виджета со топологией **список слева + детальная карточка справа** и опционально **сетка + модалка**. Паттерн совпадает с архитектурой `profiles-widget` в `@april/profile-ui`; эталонная спецификация и ссылки на код: [`profile/profiles-widget.md`](./profile/profiles-widget.md).

---

## 1. Цель паттерна

Собрать виджет, который:

- ведёт **server-driven** список (поиск, фильтры, курсор, сортировка);
- показывает **детальную карточку** выбранного элемента с чтением и мутациями;
- **не смешивает** транспорт (HTTP/SDK) с UI;
- **отменяет** устаревшие запросы (`AbortController` и учёт гонок);
- отдаёт хосту **события** (действия, ошибки, телеметрия).

---

## 2. Слои (разделение ответственности)

| Слой | Роль | Меняется при другом объекте |
|------|------|-----------------------------|
| **Публичный фасад** | Имя экспорта, тип пропсов, точка входа для embed. | Имя пакета / виджета. |
| **`*ApiWidget`** | Один раз создать **провайдер** на базовый URL; собрать **`providerContext`** (tenant, telemetry); **токен через `ref` + getter**, чтобы обновление токена (например Keycloak) **не пересоздавало** провайдер и не дёргало лишние эффекты. | Поля контекста под ваш BFF. |
| **`*WidgetCore`** | State списка, вызовы `provider.list`, layout (две колонки / сетка + модалка), **`selectedId`**, связь с детальной карточкой (props + `ref` + колбэки), **abort** запросов списка. | Колонка списка, фильтры, поля строки. |
| **`*WidgetDetailCore`** | Загрузка сущности `get`, доп. данные (версии, схемы), формы, CRUD, **abort** запросов детали, при необходимости императивный **`openCreate` / `closeCreate`**. | DTO, форма, валидация. |
| **`*DataProvider`** | Интерфейс: `list`, `get`, опционально `create` / `update` / `remove`, вспомогательные методы под селекты и схемы. | Сигнатуры, коды ошибок. |
| **Реализация провайдера** | OpenAPI или fetch, нормализация ответов API в типизированные ошибки. | Эндпоинты, маппинг DTO. |

**Правило:** Core и DetailCore **не импортируют** конкретный HTTP-клиент — только интерфейс провайдера.

---

## 3. Контракт с хостом

**Вход:** `hostContext` (минимум `tenant.id`; опционально `auth`, `telemetry`), параметры первой загрузки списка (`pageSize`, начальные фильтры и сортировка, флаги вроде `autoSelectFirst`), при необходимости `accessToken`.

**Выход:**

- **`onAction`** — дискретные события домена (`created` / `updated` / `deleted`);
- **`onError`** — безопасное сообщение для UI, плюс `requestId` и `code` для логов;
- **`onObservability`** — структурированные события (список, детальная карточка, сохранение);
- опционально **`onOpenEntity(id)`** — синхронизация URL или оболочки хоста при выборе строки.

Список по умолчанию — **только с сервера** через `provider.list`; не подменять полный каталог клиентской выборкой «все строки», если это не осознанное продуктовое решение.

---

## 4. `ProviderContext` и отмена запросов

В контекст каждого вызова провайдера передавайте как минимум:

- `tenantId`, `auth`, `telemetry`;
- **`signal: AbortSignal`** — до реального сетевого запроса.

Один и тот же интерфейс подходит для продакшена, моков и unit-тестов.

---

## 5. Алгоритм списка в Core

1. **Состояние:** `items`, `loading`, `loadingMore`, `error`, параметры запроса, `nextCursor`, `totalCount`, `selectedId`, опционально режим вида (`list` | `grid`).

2. **`loadList({ cursor, append })`:**
   - увеличить **монотонный номер запроса**;
   - **abort** предыдущего контроллера, создать новый `AbortController`, передать `signal` в `provider.list(...)`;
   - после `await`: если номер запроса **не совпадает** с текущим — **не обновлять** state;
   - при `signal.aborted` — выйти без показа ошибки пользователю;
   - при `append` — дописать страницу с **дедупликацией** по стабильному ключу строки;
   - при необходимости — телеметрия: `list_requested` / `list_succeeded` / `list_failed` (и при первой полной загрузке, например, `view_loaded`).

3. **Эффект перезагрузки списка** зависит от всего, что меняет запрос: провайдер, tenant, `pageSize`, поиск, фильтры, сортировка, политика `autoSelectFirst`.

4. **Политика выбора после успешного `loadList`:**
   - если задан **предпочтительный id** (например только что созданная сущность) и он есть среди `items` — выбрать его и сбросить ref;
   - иначе если текущий `selectedId` всё ещё присутствует в списке — оставить;
   - иначе при `autoSelectFirst` — первая строка;
   - иначе `null`.

5. **Пагинация:** по событию «дошли до конца списка» — при наличии `nextCursor` и отсутствии активной подгрузки вызвать `loadList({ append: true, cursor: nextCursor })`.

6. **Снятие выбора:** для master–detail часто **игнорируют `null`** в обработчике выбора (toggle в компоненте списка), чтобы не ломать первый клик при `autoSelectFirst`.

---

## 6. Детальная карточка (DetailCore)

1. **`useEffect` по `selectedId`:** при `null` — полный сброс локального state; иначе abort предыдущего запроса, затем `get(id, { signal })`.

2. **Дополнительные данные** (версии, схемы) — отдельные async-цепочки с тем же `signal` и защитой от гонок (счётчик запроса или сравнение актуального `id`).

3. **После мутаций:** вызвать `onAction`, затем уведомить родителя для **`loadList` без append** (или узкий патч списка, если так зафиксировано).

4. **`useImperativeHandle`:** `openCreate` / `closeCreate`, если создание должно открываться с **кнопки списка**, из **сетки** или с **хоста**, а не только изнутри карточки.

5. **Вложенный chrome:** если родитель уже показывает оболочку (например модалку в режиме сетки), детальная карточка получает флаги вроде «не открывать вторую модалку», «портал тулбара в шапку родителя» — один уровень модальных/шапочных решений.

---

## 7. Режим «сетка + модалка» (опционально)

- В **grid** список на полную ширину, колонка детальной карточки **скрыта**, сама карточка в **модальном окне**.
- Модалка открыта при **`selectedId`** или при **сессии «создать без выбранной строки»**.
- **При входе в grid** — сброс выбора и сессий создания, чтобы модалка **не открылась сразу** после переключения вида.
- **При закрытии модалки** — сброс выбора и вызов `closeCreate` у вложенного потока создания.
- **При возврате в list** выбор может **сохраниться**, если пользователь не сбрасывал его закрытием модалки (политика продукта; так задокументировано для `profiles-widget`).

---

## 8. Стабильность провайдера и токена

- Провайдер: `useMemo(() => createProvider({ baseUrl }), [baseUrl])` — **без** токена в массиве зависимостей.
- Токен: хранить в `useRef`, на каждом рендере `ref.current = token`, в `providerContext.auth` отдавать **getter** `accessToken`, чтобы смена токена не пересоздавала фабрику провайдера.

---

## 9. Ошибки и безопасность UI

Маппинг кодов провайдера (`unauthorized`, `forbidden`, `conflict`, …) в **короткие пользовательские сообщения**. В телеметрию и логи — `requestId`, `code`. Не показывать в UI сырые внутренние сообщения бэкенда.

---

## 10. Тестирование

- **Core** и **DetailCore** — с **in-memory** или mock-реализацией `*DataProvider`, без сети.
- Сценарии: гонки при быстрой смене фильтра, unmount и abort, `autoSelectFirst`, create/delete и обновление выбора, режим сетки и `openCreate`.

---

## 11. Чеклист: новый домен, та же топология

1. Ввести типы: **`ThingListItem`**, **`ThingDetails`**, **`ThingListQuery`**, **`ThingListPage`**.
2. Описать интерфейс **`ThingDataProvider`**: `list` / `get` / мутации + **`ProviderContext`** с **`signal`**.
3. Реализовать **`createOpenApiThingProvider`** (или аналог) и маппинг ошибок.
4. **`ThingApiWidget`**: провайдер + ref-токен + сборка `providerContext`.
5. **`ThingWidgetCore`**: state списка, abort, выбор, встраивание **`ThingWidgetDetailCore`**.
6. **`ThingWidgetDetailCore`**: эффект на `selectedId`, формы, ref для create, колбэки ревалидации списка.
7. Публичный **`ThingWidget`** = `ThingApiWidget`.
8. Документация: топология, server-only список, политика выбора, опционально сетка и модалка; ссылки на `TASK`/`REPORT` по мере появления.
