## Исходные допущения
- Задача 042 закрыта, архитектура/контракты утверждены.
- Задача 043 закрыта, list endpoint и SDK готовы.

- Основной UX (master-detail, CRUD) сохраняется; меняется только архитектура и data-source модель.

## Порядок работ (шаги)
1. Подготовить доменные типы и provider контракты в `profile-ui`.
2. Выделить новый компонент `ProfilesWidgetCore`:
   - перенести UI/state logic из текущей реализации;
   - исключить прямые API вызовы;
   - подключить provider-интерфейс.
3. Реализовать `openapiProfilesProvider`:
   - list/get/create/update/remove;
   - error normalization;
   - request context wiring.
4. Реализовать `ProfilesApiWidget`:
   - конструирование provider;
   - маппинг host props -> provider context;
   - передача callbacks/observability в `Core`.
5. Обновить публичный экспорт:
   - `ProfilesWidget` как facade на `ProfilesApiWidget`;
   - удалить `entityIds` из публичных пропсов.
6. Мигрировать demo route:
   - убрать `VITE_PROFILE_LIST_DEMO_ENTITY_IDS` из сценария источника данных;
   - сохранить только host-конфиг.
7. Переписать тесты:
   - unit для `Core` через mock provider;
   - integration для adapter;
   - регрессии на UX сценарии.
8. Обновить документацию и task-story материалы.
9. Прогнать проверки и зафиксировать gate-результаты.

## Риски и откат
- **Риск:** регрессия UX при миграции на provider-модель.  
  **Митигация:** сохранить существующие пользовательские сценарии и покрыть регресс-тестами.
- **Риск:** гонки запросов list/details при быстрых действиях пользователя.  
  **Митигация:** централизованная отмена in-flight запросов + тесты на race scenarios.
- **Риск:** скрытые зависимости на `entityIds` в демо/тестах.  
  **Митигация:** удалить поле из контрактов и компиляционно проверить отсутствующие usages.
- **Откат:** revert refactor-коммита целиком с возвратом предыдущего контракта (только если релиз блокирован), затем новый инкрементальный rollout.
