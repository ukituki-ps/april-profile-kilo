# Задача: Фаза 4.3 — модель описания виджетов и погружение в документацию проекта

## Мета
- **ID / ветка:** (например `feat/phase-4-widget-docs-model`)
- **Приоритет:** обычный
- **Родительская дорожная карта:** [`tasks/000-full-service-aprilhub-roadmap/`](../000-full-service-aprilhub-roadmap/) — продолжение Фазы 4 после технической интеграции (`020`-`023`), фокус на документационном контуре и эксплуатационной понятности.
- **Связанные подзадачи:** опирается на [`020-phase-4-profile-contract-behind-hub-bff`](../020-phase-4-profile-contract-behind-hub-bff/), [`022-phase-4-profile-ui-package-openapi-embed`](../022-phase-4-profile-ui-package-openapi-embed/), [`023-phase-4-aprilhub-widget-host-e2e-smoke`](../023-phase-4-aprilhub-widget-host-e2e-smoke/).
- **Связанные документы:** [`docs/WIDGET_CONTRACTS.md`](../../docs/WIDGET_CONTRACTS.md), [`docs/WIDGET_INTEGRATION_CHECKLIST.md`](../../docs/WIDGET_INTEGRATION_CHECKLIST.md), [`docs/VERSIONING_AND_COMPATIBILITY.md`](../../docs/VERSIONING_AND_COMPATIBILITY.md), [`docs/WIDGET_OBSERVABILITY_GUIDE.md`](../../docs/WIDGET_OBSERVABILITY_GUIDE.md).

## Цель
Зафиксировать единый стандарт описания виджетов (для случаев, когда на один профиль приходится несколько виджетов) и внедрить его в документацию проекта: строгая каноническая версия в `docs/` для агентов и команды, а человекопонятная адаптация в `docs-site/` для интеграторов и продуктовой коммуникации.

## Контекст для агента
- В проекте уже есть техническая база контрактов и интеграции виджетов, но нет единой структуры каталога виджетов по профилям (`profile -> widgets -> versions/status`).
- Нужна синхронизация двух слоев документации без расхождения смысла: `docs/` как source of truth и `docs-site/` как адаптированная под человека версия.

## Входит в объём
- Утвердить и описать **операционную модель документации виджетов**:
  - идентификаторы (`profileId`, `widgetId`, `contractVersion`);
  - статус жизненного цикла (`draft | beta | stable | deprecated`);
  - обязательные разделы карточки виджета (назначение, props/events, права доступа, зависимости, observability, ограничения, known issues);
  - правила совместимости и change policy (breaking/non-breaking).
- Описать **структуру хранения** в `docs/`:
  - индекс по профилям и виджетам;
  - карточки виджетов в едином шаблоне;
  - явные ссылки на `TASK/PLAN/REPORT` и связанный e2e/smoke.
- Описать **структуру подачи** в `docs-site/`:
  - человекопонятный каталог и навигация;
  - формат "что это, зачем, как подключить, как проверить";
  - связи со страницами task-story.
- Добавить/обновить шаблоны и чеклисты документации, чтобы новые виджеты добавлялись по одному процессу.
- Зафиксировать Definition of Done для документационного потока при выпуске/изменении виджета.

## Не входит в объём
- Новая реализация backend/frontend функциональности виджетов.
- Переработка OpenAPI-контракта API без отдельной постановки.
- Полная миграция архивных документов за пределами контура виджетов (если не требуется для целостности нового формата).

## Технические ограничения
- `docs/` остаётся каноническим источником для агентных и инженерных решений.
- `docs-site/` не должен искажать контрактные требования из `docs/`.
- Термины, статусы и идентификаторы должны быть одинаковыми в обоих слоях.
- Любое несовместимое изменение в модели описания виджетов фиксируется через версионирование и changelog.

## Критерии готовности (acceptance)
- [ ] В `docs/` описана целевая модель документации виджетов (структура, обязательные поля, статусы, версия, DoD).
- [ ] В `docs/` есть индексная точка входа по профилям/виджетам и шаблон карточки виджета.
- [ ] В `docs-site/` опубликована человекопонятная версия этой модели с примерами "как читать/как применять".
- [ ] В чеклистах релиза/интеграции добавлены шаги синхронизации `docs` и `docs-site`.
- [ ] Для уже реализованных виджетов создан или обновлён каталог артефактов (минимум ссылки на контракт, интеграцию, smoke/e2e, task-story).
- [ ] `make docs-build` зелёный, а ссылки между страницами валидны.
