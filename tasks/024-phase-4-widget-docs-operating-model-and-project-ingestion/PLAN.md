# План: Фаза 4.3 — модель описания виджетов и погружение в документацию проекта

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-24
- **Статус плана:** согласован

## Исходные допущения
- Канонический слой описаний виджетов живёт в `docs/`, `docs-site/` публикует адаптированную версию без изменения терминов и контрактных требований.
- Текущий набор артефактов для примеров берём из задач `022` и `023` (widget package + host/e2e поток в AprilHub).
- Задача документарная: код backend/frontend и миграции Atlas не требуются.

## Порядок работ (шаги)
1. Зафиксировать операционную модель `profile -> widgets -> version/status` в новой канонической странице `docs/`.
2. Описать структуру хранения: индекс каталога, шаблон карточки, ссылки на `TASK/PLAN/REPORT` и smoke/e2e артефакты.
3. Добавить стартовый каталог текущего профиля/виджета по шаблону и связать с существующими документами.
4. Синхронизировать человекопонятный слой в `docs-site/` (каталог, как читать, как применять).
5. Обновить чеклисты релиза/интеграции виджетов шагами синхронизации `docs` + `docs-site`.
6. Подготовить task-story, обновить `task-stories-overview`, отметить задачу в `task_list.md`, собрать `REPORT.md`.
7. Прогнать `make docs-build` и зафиксировать результат в отчёте.

## Риски и откат
- **Риск:** расхождение терминов между `docs/` и `docs-site/` → **Митигация:** использовать единый словарь (`profileId`, `widgetId`, `contractVersion`, lifecycle status) и перекрёстные ссылки.
- **Риск:** устаревшие ссылки на внешние артефакты `023` → **Митигация:** указывать статус и owner-репозиторий рядом со ссылками.
- При необходимости отката: удалить новые страницы и вернуть чеклисты/индекс к предыдущему состоянию.

- Команды: `make docs-build`
- Ручная проверка: пройтись по ссылкам в новых страницах `docs/` и `docs-site/`, убедиться в совпадении модели и терминов.
