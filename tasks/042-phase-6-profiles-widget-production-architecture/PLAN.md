# План: production-архитектура `ProfilesWidget` (Core + API adapter)

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-29
- **Статус плана:** согласован

## Исходные допущения
- Текущая реализация `ProfilesWidget` функционально рабочая, но архитектурно опирается на demo-friendly вход `entityIds`.
- В `frontend/packages/profile-ui/src/generated/services/ProfilesService.ts` сейчас есть CRUD по конкретному entity, но отсутствует list/search endpoint в текущем SDK.
- Команда готова сознательно сломать backward compatibility ради корректной production-архитектуры.
- `Core` должен быть полностью независим от `OpenAPI.BASE`, `OpenAPI.TOKEN`, env и backend DTO.

## Порядок работ (шаги)
1. Зафиксировать целевую архитектурную модель:
   - `ProfilesWidgetCore` (UI + state machine),
   - `ProfilesApiWidget` (adapter),
   - `ProfilesWidget` (public facade).
2. Утвердить доменный типовой слой:
   - list item/details/query/page/mutation/error types;
   - правила маппинга provider error -> UI-safe message.
3. Утвердить контракт `ProfilesDataProvider`:
   - `list/get/create/update/remove`;
   - контекст вызова (`tenant`, `auth`, `telemetry`, `AbortSignal`);
   - требования к пагинации (cursor-based) и серверным фильтрам.
4. Утвердить state-machine поведение `Core`:
   - загрузка списка и детальной карточки;
   - отмена устаревших запросов;
   - поведение при create/update/delete;
   - консистентность списка, детальной карточки (list/detail) и выбора.
5. Утвердить observability-контракт:
   - обязательные события;
   - обязательные поля meta;
   - request/correlation правила.
6. Зафиксировать anti-patterns и запреты:
   - отсутствие `entityIds` в публичном API;
   - отсутствие транспортной логики внутри `Core`;
   - запрет demo-config в runtime контрактах.
7. Обновить документацию (`docs`, `docs/widgets`, package README) как технический baseline для задач 043/044.
8. Провести архитектурный review-checkpoint: без него 043/044 не стартуют.

## Риски и откат
- **Риск:** контракт будет слишком общим и позволит альтернативные трактовки.  
  **Митигация:** формализовать обязательные/запрещённые пункты и конкретные интерфейсы.
- **Риск:** реализация 043 начнется без согласованных backend preconditions.  
  **Митигация:** в acceptance добавить hard gate: список API preconditions обязателен.
- **Риск:** часть legacy-предположений сохранится неявно в документации.  
  **Митигация:** явный раздел «что удаляется/запрещено».
- **Откат:** если архитектура признана несостоятельной, план помечается `устарел`, создается новый TASK с альтернативой и формальным сравнением.
