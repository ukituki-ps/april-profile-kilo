# Задача: Фаза 2 (часть 4) — ABAC-фильтрация выдачи по сегментам полей

## Мета
- **ID / ветка:** (например `feat/phase-2-abac-field-filtering`)
- **Приоритет:** высокий
- **Родительская дорожная карта:** [`tasks/000-full-service-aprilhub-roadmap/`](../000-full-service-aprilhub-roadmap/) — [`PLAN.md`](../000-full-service-aprilhub-roadmap/PLAN.md), **Фаза 2**, блок **«Затем»** (фильтрация выдачи по ABAC, сегменты полей).
- **Связанные подзадачи:** зависит от [`011-phase-2-entity-crud-versioning`](../011-phase-2-entity-crud-versioning/) и [`012-phase-2-authority-merge-conflicts`](../012-phase-2-authority-merge-conflicts/).
- **Связанные документы:** [`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md), [`docs/adr/0002-april-profile-scope-and-multitenancy.md`](../../docs/adr/0002-april-profile-scope-and-multitenancy.md)

## Цель
Ввести ABAC-фильтрацию на чтении профиля: разные роли/атрибуты доступа получают разные сегменты полей, при этом ответ API остаётся валидным и предсказуемым, а правила доступа можно проверить автоматическими тестами.

## Контекст для агента
- Опора на фазу 2, блок «Затем» в [`../000-full-service-aprilhub-roadmap/PLAN.md`](../000-full-service-aprilhub-roadmap/PLAN.md).
- Keycloak остаётся источником ролей/признаков доступа; нельзя заменять IAM-модель на кастомную auth-схему.

## Входит в объём
- Политика ABAC на уровне сегментов полей (минимально необходимый набор ролей/атрибутов).
- Применение фильтрации в read-endpoints доменного API.
- Явное поведение API при частичной доступности данных (например, скрытые поля не возвращаются или возвращаются маскированно по согласованному контракту).
- Тесты на видимость полей по ролям/атрибутам и tenant-контексту.
- Актуализация OpenAPI/документации, если меняется форма ответа или правила доступа.

## Не входит в объём
- Полноценный UI-редактор ABAC-политик.
- Внешний PDP/OPA и сложные cross-service policy engines (если отдельно не согласовано ADR).
- Событийная реакция на изменение политик (фаза 3+).

## Заглушки и внешние зависимости
- Если claims/атрибуты Keycloak для всех ролей ещё не заведены на стенде, допускается mock-набор claims в тестах и фиксированный mapping в конфиге как временный слой.
- Если часть полей ещё не классифицирована по сегментам, допускается дефолт deny/allow стратегия по согласованию, с явной фиксацией в `REPORT.md`.

## Технические ограничения
- Не допускать утечки чувствительных полей при любых ошибках фильтра.
- Tenant-изоляция и ABAC применяются совместно, а не по отдельности.
- Конфигурация политик через env/конфиг репозитория без коммита секретов.
- OpenAPI должен быть синхронизирован с фактическим поведением API.

## Критерии готовности (acceptance)
- [ ] Для целевых ролей/атрибутов определены и применяются правила видимости полей.
- [ ] Read API возвращает только разрешённые сегменты полей.
- [ ] Негативные сценарии (нет прав, неполные claims) обрабатываются предсказуемо.
- [ ] Тесты на ABAC-фильтрацию проходят и предотвращают регрессии.
- [ ] OpenAPI/доки актуальны для consumer-команд.
