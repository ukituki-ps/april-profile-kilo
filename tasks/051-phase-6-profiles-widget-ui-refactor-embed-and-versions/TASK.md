# Задача 051 (фаза 6): рефакторинг UI `ProfilesWidget` — встраивание, компоновка, версии и имя профиля

## Мета
- **ID / ветка:** `feature/task-051-phase-6-profiles-widget-ui-refactor-embed-and-versions`
- **Приоритет:** обычный
- **Связанные документы:** [`task_list.md`](../../task_list.md), [`tasks/047-phase-6-profiles-widget-test-matrix-and-release-gate/TASK.md`](../047-phase-6-profiles-widget-test-matrix-and-release-gate/TASK.md), [`docs/widgets/profile/profiles-widget.md`](../../docs/widgets/profile/profiles-widget.md), [`frontend/packages/profile-ui/README.md`](../../frontend/packages/profile-ui/README.md)

## Цель
Привести UI `ProfilesWidget` (`ProfilesWidgetCore`) к поведению удобному для встраивания в хост (не только полноэкранный демо): корректное заполнение доступной высоты и ширины при сворачивании списка, убрать отладочные заголовки, улучшить карточку профиля (редактор до низа панели, действия через иконки), добавить работу с версиями профиля и отображаемым именем, упростить создание профиля через выбор типа сущности из списка.

## Контекст для агента
- Точка входа UI: [`frontend/packages/profile-ui/src/components/ProfilesWidgetCore.tsx`](../../frontend/packages/profile-ui/src/components/ProfilesWidgetCore.tsx) — колонка списка (`CardListColumn` из `@april/ui`), правая колонка с карточкой и модалка создания.
- Сейчас заголовок «Profiles list widget» и строка «Tenant: …» заданы статично в корне разметки; первичный ключ сущности показывается как заголовок пункта списка (`listItems.title = entityId`).
- Паттерн загрузки нескольких версий по числу текущей версии уже есть в [`frontend/packages/profile-ui/src/components/InstanceHistoryWidget.tsx`](../../frontend/packages/profile-ui/src/components/InstanceHistoryWidget.tsx) (параллельные `GET /v1/entities/{id}/versions/{n}`); в OpenAPI есть только `GET …/versions/{version}`, без aggregate-list версий — при реализации селектора версий либо переиспользовать этот паттерн, либо согласовать расширение API/SDK (см. объём).
- Провайдер: [`frontend/packages/profile-ui/src/providers/profilesDataProvider.ts`](../../frontend/packages/profile-ui/src/providers/profilesDataProvider.ts); `openapiProfilesProvider` при `update` сейчас не прокидывает `expectedVersion` в тело запроса (комментарий о forward compatibility) — при доработке «восстановить как новую версию» свериться с фактическим контрактом бэкенда и SDK.

## Входит в объём

### 1. Высота и встраивание по вертикали
- Корневой layout виджета должен занимать **всю доступную высоту** контейнера хоста (типично: `height: 100%` / flex column с `minHeight: 0` у скроллируемых зон), чтобы список профилей и область карточки использовали вертикаль без «обрезания» середины при неполноэкранном embed.
- Внутренний скролл — у колонки списка и/или области документа по согласованному UX (без двойных скроллбаров без необходимости).

### 2. Сворачивание списка влево (collapse)
- При схлапывании/узкой левой колонке (`CardListColumn` / поведение `@april/ui`) **правая часть должна расширяться** и заполнять освободившееся горизонтальное пространство — не оставлять пустую полосу справа от списка.
- Проверить в связке с пропсами ширины (`defaultWidthPercent`, `minWidthPercent`, и т.д.) и при необходимости скорректировать обёртку (`Box`/`Stack`) или параметры `CardListColumn`.

### 3. Убрать отладочные подписи
- Удалить из UI виджета строки **«Profiles list widget»** и **«Tenant: …»** (сейчас в `ProfilesWidgetCore` около корневого `Stack`).
- При необходимости отладочная информация остаётся только в telemetry / dev-демо странице, не в production-разметке виджета.

### 4. Поле ввода в Profile card до низа экрана
- Редактор JSON (`Textarea` в режиме редактирования и read-only просмотр) должен **растягиваться до нижней границы** доступной области карточки (flex: `1`, `minHeight: 0`, осмысленный `max` высоты через родителя).
- Иконочная панель действий — компактная зона сверху или сбоку; основное место отдаётся документу.

### 5. Select версий и переключение; кнопка «сделать версию v+1»
- Добавить **Select** (или эквивалент из `@april/ui` / Mantine, в духе DS) со списком версий выбранного профиля и переключением просматриваемой версии.
- При выборе **не последней** (исторической) версии показывать документ этой версии (read-only или с явным режимом редактирования — зафиксировать в PLAN по согласованию с конфликтами optimistic concurrency).
- Кнопка вида **«Сделать текущей» / «Новая версия (+1)»** при просмотре старой версии: инициирует операцию создания **новой** версии на основе содержимого выбранной (семантика — как принято в домене: `PUT` с телом документа старой версии; при необходимости уточнить и дополнить контракт/SDK, если текущий API недостаточен).
- Загрузка списка номеров версий: по умолчанию допустим паттерн как в `InstanceHistoryWidget` (диапазон `1..currentVersion`); если это неприемлемо по производительности — вынести в отдельную подзадачу endpoint «перечислить версии» в OpenAPI и бэкенде.

### 6. Текстовые кнопки → иконки
- Заменить подписи **Edit profile**, **Delete profile**, **Save changes**, **Cancel** на **иконки** с доступными подписями (`aria-label` / `title` tooltip) для скринридеров и понятности.

### 7. Параметр «имя профиля», уникальность
- Ввести явное **отображаемое имя профиля** (источник данных: согласованное поле в `document`, например `name`, или отдельное поле в API — выбрать минимально инвазивно и зафиксировать в PLAN).
- **Уникальность** имени в пределах tenant (и при необходимости в связке с `entity_type_id`) — предпочтительно с **серверной** валидацией и понятной ошибкой в UI; если на момент задачи API не поддерживает — зафиксировать временную клиентскую проверку + follow-up на бэкенд (не оставлять без явного пункта в REPORT).

### 8. Список профилей: имя и версия вместо ID
- В списке слева в заголовке/основной строке пункта показывать **имя** (из п.7) и **версию**; **не использовать `entityId` как primary label** (допустимо вторичной строкой или в tooltip при отладке).

### 9. Create profile: Entity type ID → Select
- В модалке создания заменить свободный ввод **Entity type ID** на **Select** с опциями типов сущностей.
- Источник опций: существующий контракт (каталог типов / list из provider / статический список из демо — уточнить по [`openapi`](../../openapi/openapi.yaml) и текущему `openapiProfilesProvider`); при отсутствии готового метода — минимально добавить вызов в provider и мок для тестов.

## Не входит в объём
- Изменения в AprilHub shell вне репозитория (кроме заметок для интеграторов в docs виджета).
- Полная замена JSON-редактора на схемно-ориентированную форму (если не выплывает как необходимое следствие — отдельная задача).
- Миграции БД и крупный рефактор доменной модели без явной необходимости для п.7 — только если согласовано с backend-контрактом.

## Технические ограничения
- Frontend/UI: **DS-first** — `@april/ui`, Mantine в рамках принятого стека; иконки — из согласованного набора (например `@tabler/icons-react`, если уже в зависимостях пакета).
- Не ослаблять release-gate задачи 047: обновить/дополнить тесты (`ProfilesWidgetCore`, provider, smoke) под новый UI и поведение.
- Локализация строк UI — по текущей практике пакета (если строки захардкожены по-английски — сохранить единообразие до отдельной i18n-задачи).
