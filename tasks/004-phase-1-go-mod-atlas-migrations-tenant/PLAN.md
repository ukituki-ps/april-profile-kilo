# План: Фаза 1 (часть 1) — Go-модуль, Atlas, миграции tenant

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-20
- **Статус плана:** согласован (реализация: `cmd/`, `internal/`, Atlas через Docker-образ `arigaio/atlas:0.32.0`)

## Исходные допущения
- Фаза 0 дала согласованные пути и имена в [`docs/guides/PROJECT_DEFAULTS.md`](../../docs/guides/PROJECT_DEFAULTS.md); деплой на dev описан в [`docs/DEPLOYMENT_STRATEGY.md`](../../docs/DEPLOYMENT_STRATEGY.md).
- Мультитенантность и обязательный `tenant_id` — ADR-0002; детали сущностей — `DESIGN_AprilProfile` и ADR-0003 (без полной метамодели в этой задаче).

## Порядок работ (шаги)
1. Зафиксировать минимальную структуру репозитория: `go.mod`, модульный монолит (`cmd` + `internal`), единая точка входа (даже если пока без HTTP).
2. Подключить Atlas: конфигурация репозитория, каталог версий миграций, команды lint/apply для локальной проверки.
3. Спроектировать первую миграцию: таблицы/индексы под **tenant** и **заготовку** доменных таблиц (минимум полей, без преждевременного scope фазы 2).
4. Обновить `Makefile` и/или `README` с командами `go build`, миграций; не ломать существующие цели `make openapi-lint`, `make docs-build`.
5. Проверить `go vet`, `go build`, при необходимости — применение миграций к локальному Postgres.

## Риски и откат
- **Риск:** имена таблиц разойдутся с фазой 2 → **Митигация:** сверка с `DESIGN_AprilProfile` и минимальный scope; при сомнении — узкие имена + комментарий в миграции.
- **Риск:** дублирование Atlas с другим сервисом → **Митигация:** один каталог миграций в этом репозитории, без ручного SQL вне Atlas.
- Откат: откат миграций по процедуре Atlas/down при неуспехе на dev ([`DEPLOYMENT_STRATEGY.md`](../../docs/DEPLOYMENT_STRATEGY.md) §6).
