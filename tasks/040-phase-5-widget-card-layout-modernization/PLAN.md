# План: модернизация `widget-card` в двухколоночный master-detail UX

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-28
- **Статус плана:** согласован

## Исходные допущения

- Целевой `widget-card` в текущем коде реализован как `ProfilesListWidget` внутри `@april/profile-ui`.
- API-контракт backend достаточно стабилен: нужны только существующие CRUD-операции `ProfilesService`.
- Для DS-first используем `CardListColumn` из `@april/ui`, включая его паттерн incremental loading (`onReachListEnd`) вместо внешнего пагинатора.

## Порядок работ (шаги)

1. Перестроить `ProfilesListWidget` в layout 25/75 (слева список, справа карточка выбранного профиля).
2. Интегрировать `CardListColumn` слева и реализовать поиск/фильтрацию/incremental loading/выбор в его паттерне.
3. Реализовать правую карточку с режимами просмотра и редактирования, отдельными состояниями `loading/empty/error`.
4. Перенести создание профиля в модальное окно, открываемое по кнопке "плюс" в `CardListColumn`.
5. Обновить RTL-тесты под новый UX (выбор, поиск/пагинация, create/update/delete, API-ошибки).
6. Обновить документацию (`README` пакета и docs-site story), подготовить `REPORT.md`.

## Риски и откат

- **Риск:** регрессия существующих CRUD-сценариев из-за смены UI-потока → **Митигация:** обновлённые RTL-тесты на create/update/delete + ошибки.
- **Риск:** сложность тестирования DS-компонента в Vitest из-за React-контекста design-system → **Митигация:** в тестах виджета мок `@april/ui` на уровень контракта взаимодействия.
- При необходимости отката: revert изменений `ProfilesListWidget`, тестов и документации в одном PR.

## Проверка после выполнения

- Команды:
  - `cd frontend && npm run lint && npm run test && npm run build`
- Ручная проверка:
  - слева отображается список профилей в `CardListColumn`;
  - справа открывается карточка выбранного профиля;
  - кнопка "плюс" открывает модалку создания;
  - после create новый профиль выбирается автоматически;
  - догрузка списка происходит при достижении конца колонки (`onReachListEnd`).
