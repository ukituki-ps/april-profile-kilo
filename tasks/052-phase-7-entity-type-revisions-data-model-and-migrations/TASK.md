# Задача 052 (фаза 7): данные и миграции — семейства типов, ревизии схемы, привязка `entity`

## Мета

- **ID / ветка (рекомендуется):** `feature/task-052-phase-7-entity-type-revisions-data-model-and-migrations`

## Цель

Ввести в PostgreSQL и доменную модель **целевую** архитектуру типов: **семейство логического типа** (`namespace` + `code` в рамках `tenant_id`) + **линия неизменяемых опубликованных ревизий схемы** (`revision_no`) + редактируемый **черновик до публикации** + колонка/ссылка у **`entities`**, фиксирующая **к какой опубликованной ревизии** привязана сущность. Обеспечить **миграционный перенос** с текущей таблицы `entity_types` (draft/published в одной строке) без потери данных и с предсказуемым поведением для уже существующих строк `entities` / `profile_versions`.

## Жёсткие запреты (обязательно соблюдать)

Нарушение любого пункта считается **невыполнением задачи**:

1. **Запрещены «временные» таблицы или параллельные источники истины** вроде «оставим старую `entity_types` мастером, а новую таблицу для UI». После миграции должен быть **один согласованный** путь хранения, соответствующий ADR-0005 (допустимы вспомогательные таблицы истории/черновиков, но не дублирование мастер-метамодели).
2. **Запрещено** удалять или обнулять данные ради простоты миграции без явного пошагового переноса и проверок (никаких `TRUNCATE` прод-данных).
3. **Запрещено** ослаблять FK/изоляцию tenant: любые новые FK должны сохранять паттерн `(tenant_id, …)` где это уже установлено в репозитории.
4. **Запрещено** планировать «потом привяжем entity»: в результате этой задачи у каждой существующей `entity` должна быть **валидная** привязка к **опубликованной** ревизии, соответствующей её предыдущему `entity_type_id` (семантика переноса описать в PLAN/комментариях миграции SQL).
5. **Запрещены MVP-обрезания** («сделаем только таблицу ревизий без bind на entities», «оставим совместимость только для новых сущностей»).

## Входит в объём

### 1. Проектирование таблиц (Atlas)

Зафиксировать в PLAN точные имена; ориентир (можно уточнить в PLAN при нормализации имён):

- **`entity_type_families`** (или эквивалент): `id`, `tenant_id`, `namespace`, `code`, `created_at`, `updated_at`, UNIQUE (`tenant_id`, `namespace`, `code`).
- **`entity_type_revisions`**: `id`, `tenant_id`, `family_id`, `revision_no` (монотонно в семействе, с 1), `schema_json` (immutable после вставки), `published_at`, опционально `published_by`/текстовые метки если есть стандарт в проекте, UNIQUE (`tenant_id`, `family_id`, `revision_no`).
- **`entity_type_drafts`**: один черновик на семейство (или версионирование черновика — если выбрано версионирование, обосновать в PLAN; **не** оставлять неограниченный мусор без политики). Минимум: `tenant_id`, `family_id`, `draft_schema_json`, `draft_revision` / `etag` поле для optimistic concurrency, `updated_at`.
- **Изменение `entities`**: колонка `bound_entity_type_revision_id` (или согласованное имя) NOT NULL после backfill; FK на `entity_type_revisions` с участием `tenant_id` по принятому в проекте стилю.

### 2. Миграция данных

- Перенести каждую строку `entity_types` в модель семейство + минимум одна опубликованная ревизия:
  - если `status=published` — ревизия снимает `published_schema_json`/`published_schema_version` (или актуальный `schema_json`, если исторически черновик = опубликованный снимок);
  - если только `draft` — семейство + черновик; **policy** для существующих `entities`, ссылающихся на неопубликованный тип: **зафиксировать в PLAN** допустимое поведение (блокировать, запретить миграцию до ручной публикации и т.д.) — но **не** молча оставить битые FK.
- Для каждой `entities.entity_type_id` сопоставить **family** и выставить `bound_*` на ту ревизию, которая соответствует ранее опубликованному контракту (обычно максимальная опубликованная на момент миграции для этого legacy `entity_types.id`).
- После backfill — **строгие constraints** (`NOT NULL`, FK), удаление или переименование legacy колонок **только** если безопасно и сопровождается одновременным обновлением кода в задаче 053 (если код в этой задаче не трогается, оставьте временную колонку **только** при явном согласовании в PLAN как двухфазную миграцию с чёткой фазой 2 в 053 — **избегайте без явной пометки**).

Рекомендуемый паттерн: в 052 добавить новые таблицы + новые колонки + backfill; **удаление** `entities.entity_type_id` / `entity_types` — только если задача 053 в той же ветке готова; иначе в PLAN явно указать фазирование (**без противоречия запрету «временное навсегда»**).

### 3. Документация схемы

- Комментарии SQL (`COMMENT ON`) для новых таблиц и ключевых колонок по стилю существующих миграций.
- При необходимости краткий раздел в ADR или ссылка из ADR на миграционный файл (правка текста ADR только если обнаружено расхождение с реализацией).

### 4. Инварианты (проверить в SQL или последующими тестами в 053)

- Нельзя иметь две опубликованные ревизии с одинаковым `revision_no` в одном семействе.
- `revision_no` строго возрастающий при публикации (без дыр допускается или нет — зафиксировать).
- Любая `entity.bound_*` ссылается на ревизию того же `tenant_id` и того же семейства, что и логический тип этой сущности.

## Не входит в объём

- Реализация HTTP handlers и OpenAPI (задача **053**).
- UI виджета (задача **054**).
- Изменение Keycloak клиентов / маршрутов Hub (задача **055**, внешние репозитории — только документация handoff здесь при необходимости).
