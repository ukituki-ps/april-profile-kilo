## Порядок работ (шаги)
1. Определить минимальный горизонт синка (что именно «батч»: например опрос изменений во внешнем API по курсору).
2. Спроектировать таблицу checkpoints (Atlas); индексы под `(tenant_id, source_system)` или эквивалент.
3. Реализовать адаптер `SourceClient` с mock-реализацией и тестовой фикстурой.
4. Задача Asynq: прочитать батч, применить идемпотентно к домену (или только обновить лаг, если доменный импорт ещё не готов — тогда явно зафиксировать в TASK/REPORT как временный режим).
5. Экспорт Prometheus: gauge лага (текущее время − watermark источника или величина по контракту).
6. Интеграционные тесты с БД и mock-клиентом.

## Риски и откат
- **Риск:** ложный лаг из-за неверных часов → **Митигация:** монотонные cursor/checkpoint, не «только wall clock».
- **Риск:** двойная обработка батча → **Митигация:** идемпотентные ключи на стороне записи в домен (как в фазе 2 для внешних ключей).
- Откат: отключение job флагом; откат миграции по процедуре репозитория.
