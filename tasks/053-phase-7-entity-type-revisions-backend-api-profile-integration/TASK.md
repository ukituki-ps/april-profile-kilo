## Цель

Реализовать **полное целевое** серверное API для администрирования каталога типов по ADR-0005: управление семейством типа, **черновиком**, **публикацией новой immutable-ревизии**, просмотр истории ревизий; операции **`entity`**: при создании привязка к **latest published revision** семейства; **явный апгрейд** привязки на заданную (или latest) опубликованную ревизию с **валидацией документа профиля** и записью новой версии профиля при необходимости (append-only). Синхронизировать OpenAPI и сгенерированный SDK frontend-пакета. Интеграционные и HTTP-тесты покрывают критические ветви.

## Контекст для агента

- Текущие эндпоинты типов ограничены list/create draft/publish в [`internal/httpapi/server.go`](../../internal/httpapi/server.go).
- JWT/tenant middleware и контракт ошибок уже приняты проектом; **не менять модель tenant** произвольно.
- Publish типа ранее был **строго одноразовым** в доменном коде `entitytypes`; целевая модель требует **повторной публикации как новых ревизий** — адаптировать доменную логику, не сохраняя старое поведение «навсегда».

## Жёсткие запреты

1. **Запрещены временные заглушки API** («возвращаем 501», «полу-пустые схемы OpenAPI», «принимаем любой JSON без валидации»).
2. **Запрещено** оставлять `profiles` создание без учёта **bound revision** после завершения интеграции.
3. **Запрещено** смешивать tenant_id из тела запроса (как уже правило сервиса).
4. **Запрещено** добавлять «временный UI-only endpoint» без доменной семантики, если нужная операция уже часть целевой модели.
5. **Запрещено** игнорировать идемпотентность там, где в проекте уже принят паттерн (например outbox профиля) — любое изменение `profile_versions` должно оставаться согласованным с транзакциями/outbox там, где применимо.
6. **Запрещено** ослаблять проверки admin-only операций без явной конфигурации (см. существующий стиль для `/v1/admin/*` или согласованный realm-role guard).

## Входит в объём

### 1. Доменный слой типов (`internal/entitytypes` или согласованный пакет)

- Полный CRUD семейства: create/list/get/update(delete) при политике из ADR и миграции 052 (delete только если допустимо и безопасно).
- Draft: чтение, сохранение с optimistic concurrency (**обязательно** поддержать конфликт редактирования — `409` или `412` по соглашению OpenAPI **одно на весь сервис**).
- Publish: создать строку ревизии `revision_no+1`, immutability, ошибки при невалидной схеме (`422`).
- List revisions для семейства (read-only), get revision by id/`revision_no`.

### 2. Операции upgrade binding

**Single entity upgrade:**

- Вход: `entity_id`, целевая ревизия (`revision_id` или `revision_no` + `family`).
- Сервер проверяет tenant, состояние сущности.
- Валидировать текущий документ профиля (или целевую проекцию) против целевой JSON Schema заготовки `ValidateSchemaForPublication`/расширенный валидатор.
- При успехе: при необходимости — **normalize** документ → **новая версия профиля** + обновление `entities.bound_*` **в одной транзакции**; затем триггер outbox как при обновлении профиля (согласовать с существующим `insertProfileOutboxRow`).
- Отчёт ошибок `422`: структурированно (минимум: список path/message — формат зафиксировать в OpenAPI).

**Batch upgrade** (обязательно в целевом решении):

- Endpoint принимает фильтры (семейство, только «behind latest») или явный список `entity_id`, лимиты.
- Ответ: агрегированная сводка (успешно/ошибка по id), **идемпотентный ключ запроса** опционально (если принято командой).

### 3. Интеграция с профилем

- `Create` профиля: выбирает **latest published revision** выбранного семейства; отказ при отсутствии опубликованных ревизий.
- `ensureEntityTypePublished` заменить на проверку **наличия ревизии** и совместимости с bind (конкретная логика в PLAN).
- Outbox событие: включить информацию достаточную для потребителя идентифицировать **`type_key` + revision** (решение совместимо с текущими полями outbox без ломания idempotency — описать).

### 4. HTTP + OpenAPI

- Расширить [`openapi/openapi.yaml`](../../openapi/openapi.yaml) всеми путями/схемами; ошибки через единый envelope с `request_id`.
- Обновить generated SDK во frontend-пакете (команды в README пакета / существующий codegen-пайплайн).
- Интеграционные тесты: см. паттерны [`internal/httpapi/server_test.go`](../../internal/httpapi/server_test.go) и integration tests каталога `internal/integrationtest/`.

## Не входит в объект

- Разработка React-виджета (**054**).
- История AprilHub (**055** документация).
- Автоматические **transformation pipelines** между несовместимыми схемами (если понадобится — отдельная задача; в этой задаче достаточно **явного отказа** с отчётом валидации + ручное исправление документа до повторного upgrade).

## Технические ограничения

- Go: идиоматика существующих пакетов; ошибки переводятся в HTTP как в текущих handlers типов (`handlePublishEntityType` и профили).
- OpenAPI как контракт; **не расходиться** между yaml и кодом без отметки deprecation.

## Требования к дизайн-системе

- Неприменимо. **Не** добавлять React в эту задачу.

## Критерии готовности (acceptance)

- [ ] OpenAPI описывает **полный** целевой набор операций; SDK регенерен.
- [ ] Ручные/handlers-тесты: publish создаёт ревизию; повторная публикация возможна и даёт следующий `revision_no`.
- [ ] Upgrade: успех обновляет bind + даёт новую `profile_versions` версию когда документ изменился семантически (или когда политика требует — зафиксировать в PLAN); неуспех оставляет данные без изменений.
- [ ] Batch upgrade возвращает детализированную сводку.
- [ ] `go test ./...` зелёный.
- [ ] Нет временных заглушек в handlers.
