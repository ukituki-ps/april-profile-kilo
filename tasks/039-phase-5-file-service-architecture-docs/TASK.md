# Задача 039: выделить отдельный File Service в архитектуре и документации April

## Мета
- **ID / ветка:** `039-phase-5-file-service-architecture-docs`
- **Приоритет:** высокий
- **Связанные документы:** [`task_list.md`](../../task_list.md), [`docs/структура сервиса.md`](../../docs/структура%20сервиса.md), [`docs/DESIGN_AprilProfile.md`](../../docs/DESIGN_AprilProfile.md), [`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md)

## Цель
Зафиксировать в архитектуре April и в документации репозитория, что работа с файлами реализуется как отдельный сервис (вариант B: отдельный File Service), а `AprilProfile` остаётся владельцем профилей и ссылок на файлы, но не бинарного хранилища.

## Контекст для агента
- Опора на [`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md) и [`README.md`](../../README.md).
- Упомянутые файлы в Cursor: `@docs/структура сервиса.md`, `@docs/DESIGN_AprilProfile.md`, `@task_list.md`.
- Источник решения: согласованный выбор архитектурного варианта B (отдельный File Service) для хранения файлов, presign-сценариев, lifecycle и политик доступа.

## Входит в объём
- Обновить архитектурные документы, где описаны сервисные границы, и явно добавить отдельный File Service.
- Внести человекопонятное описание File Service в [`docs/структура сервиса.md`](../../docs/структура%20сервиса.md):
  - зона ответственности;
  - границы с `AprilProfile`;
  - типовые сценарии интеграции (upload/download, метаданные, доступы).
- Зафиксировать единый термин (`File Service` / `AprilFile`) и избежать неоднозначных формулировок "храним файлы в профиле".
- Обновить связанные указатели/ссылки в документации при необходимости.

## Не входит в объём
- Реализация runtime-кода нового file-микросервиса.
- Изменение API `AprilProfile` и OpenAPI контрактов в рамках этой задачи.
- Настройка инфраструктуры object storage, AV-сканирования и production-деплоя.

## Технические ограничения
- Стек и архитектурные ограничения — по [`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md).
- Изменения только в документации и task-tracking артефактах.
- Breaking-изменения существующих договорённостей не вносить; при спорных местах формулировать как "планируемое целевое состояние".
