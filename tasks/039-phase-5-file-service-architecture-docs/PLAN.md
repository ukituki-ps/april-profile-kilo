# План: зафиксировать отдельный File Service в архитектуре и документации April

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-28
- **Статус плана:** согласован

## Исходные допущения

- Задача 039 документарная: runtime-код и OpenAPI не меняются.
- Выбран архитектурный вариант B: отдельный `File Service` (рабочее имя `AprilFile`).
- Каноничные архитектурные документы находятся в `docs/`; при наличии зеркала в `docs-site/` требуется синхронное обновление.

## Порядок работ (шаги)

1. Уточнить область изменений: `docs/структура сервиса.md`, `docs/DESIGN_AprilProfile.md`, `docs/AGENT_ARCHITECTURE_CONTEXT.md`.
2. Зафиксировать в документации границы ответственности `AprilProfile` и `AprilFile` без двусмысленностей.
3. Синхронизировать человекопонятный слой документации: отдельная история задачи в `docs-site/docs/`.
4. Обновить индекс `docs-site/docs/task-stories-overview.md` (ссылка + статус).
5. Подготовить итоговый отчёт `REPORT.md` по шаблону с перечнем изменений, проверок и follow-up.

## Риски и откат

- **Риск:** терминологическая неоднозначность (`File Service` vs `AprilFile`) → **Митигация:** везде использовать формулировку "`AprilFile (File Service)`".
- **Риск:** рассинхрон между `docs/` и `docs-site/` → **Митигация:** парные изменения в каноничном и публикуемом файлах.
- При необходимости отката: revert только markdown-изменений в документации и `tasks/`.

  - новая страница `task-story-039-file-service-architecture-docs.md` ссылается на `TASK.md`, `PLAN.md`, `REPORT.md`.
