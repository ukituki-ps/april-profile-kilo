# План: Фаза 2 (часть 1) — каталог типов сущностей и публикация схем в OpenAPI

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-21
- **Статус плана:** черновик

## Исходные допущения
- Фаза 1 завершена, в сервисе уже есть tenant-контекст из JWT и базовый HTTP-каркас.
- Для каталога типов достаточно жизненного цикла `draft -> published`; версионирование профиля как доменной сущности остаётся в задаче 011.
- Валидация схемы при публикации реализуется локально (структурная проверка и инварианты из ADR-0003), без внешнего реестра схем.

## Порядок работ (шаги)
1. Добавить Atlas-миграцию для статуса публикации типа и полей опубликованной схемы.
2. Реализовать backend-каталог типов (создание draft, список, publish с tenant-изоляцией и обработкой ошибок).
3. Подключить новые handlers в HTTP API, сохранив контракт `tenant_id` только из JWT.
4. Обновить OpenAPI (`openapi/openapi.yaml`) синхронно с реализацией.
5. Добавить/обновить тесты (unit + integration smoke по возможности) для базового пути и ошибок публикации.
6. Обновить docs-site историю задачи и overview, затем оформить `REPORT.md`.

## Риски и откат
- **Риск:** Структурная валидация схемы окажется слишком мягкой/жёсткой. → **Митигация:** минимальные явные инварианты + фиксировать ограничения в `REPORT.md`.
- **Риск:** Поведение publish при повторном вызове может быть неоднозначным. → **Митигация:** стабильный `409 already_published` и тест на этот путь.
- При необходимости отката: revert миграции/кода задачи 010 и вернуть прежний OpenAPI.

## Проверка после выполнения

- Ручная проверка: создание draft типа, публикация, повторная публикация, публикация невалидной схемы.
