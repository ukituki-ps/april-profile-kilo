# План: outbox, контракт события, идемпотентность публикации

- **Задача:** [`TASK.md`](./TASK.md)
- **Дата плана:** 2026-04-21
- **Статус плана:** выполнен (код и миграции зафиксированы в репозитории)

## Исходные допущения
- Write-путь сущности и append-only версий уже есть (фаза 2); триггер события — успешная фиксация новой версии профиля (или согласованное событие «изменение»).
- Outbox — паттерн согласованности с БД; фоновая обработка и очередь задач в проекте — **Redis + Asynq** ([`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md)). Интерфейс `Publisher` (или аналог) изолирует выход к внешним потребителям; отдельный Kafka/Rabbit — только при отдельном ADR.

## Порядок работ (шаги)
1. Уточнить минимальный JSON/event struct по ADR-0003 и `DESIGN_AprilProfile.md` §4.5; зафиксировать генерацию `event_id`.
2. Спроектировать таблицу outbox (статусы, retry поля при необходимости — полная политика ретраев может дозаполняться в [`017`](../017-phase-3-async-retries-dlq/)).
3. Добавить миграции Atlas; прогнать validate локально и в CI.
4. В слое приложения: в транзакции с сохранением версии — вставка в outbox; уникальные ограничения под идемпотентность.
5. Заглушка публикации наружу: пометка «processed»/лог или noop-адаптер; перенос в Asynq — в [`015`](../015-phase-3-asynq-infra-ping-domain-task/).
6. Тесты: unit + integration (Testcontainers) по образцу фазы 1.
