# Задача: Фаза 3 (часть 1) — контракт события, outbox, идемпотентность публикации

## Мета
- **ID / ветка:** `feature/phase-3-outbox-event-contract-idempotency`
- **Приоритет:** высокий
- **Родительская дорожная карта:** [`tasks/000-full-service-aprilhub-roadmap/`](../000-full-service-aprilhub-roadmap/) — [`PLAN.md`](../000-full-service-aprilhub-roadmap/PLAN.md), **Фаза 3**, блок **«Сначала»** (контракт события по ADR-0003; transactional outbox; идемпотентность на стороне публикации). Фоновая доставка в этом репозитории опирается на **Redis + Asynq** ([`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md)), а не на отдельный классический брокер (Kafka/Rabbit) — такой контур только при отдельном ADR и согласовании.
- **Связанные подзадачи:** предшествует [`015-phase-3-asynq-infra-ping-domain-task`](../015-phase-3-asynq-infra-ping-domain-task/); опирается на завершение фазы 2 ([`010`](../010-phase-2-entity-types-openapi/)–[`013`](../013-phase-2-abac-field-filtering/)).
- **Связанные документы:** [`docs/adr/0003-april-profile-data-model-policies.md`](../../docs/adr/0003-april-profile-data-model-policies.md), [`docs/DESIGN_AprilProfile.md`](../../docs/DESIGN_AprilProfile.md) (§4.5 события), [`docs/AGENT_ARCHITECTURE_CONTEXT.md`](../../docs/AGENT_ARCHITECTURE_CONTEXT.md)

## Цель
Зафиксировать в коде и БД контракт исходящего события профиля (минимум полей из ADR-0003), обеспечить **transactional outbox** при изменении профиля и **идемпотентность на стороне публикации** (повторная запись/публикация с тем же логическим событием не создаёт дубликатов в хранилище outbox и не ломает инварианты).

## Входит в объём
- Структура события (код + при необходимости JSON-схема/комментарии в OpenAPI или `docs/`, без ломания существующего публичного REST-контракта, если отдельный канал не согласован).
- Таблица(ы) outbox и миграции **Atlas** (`atlas/migrations/`), согласованные с транзакциями доменного слоя.
- Запись строки outbox **в той же транзакции**, что и фиксация новой версии профиля (или согласованный аналог «изменение профиля → событие»).
- Идемпотентность публикации: уникальность `event_id` (и/или детерминированный ключ от `(tenant_id, entity_id, profile_version, …)` по правилам из ADR-0003), обработка конфликтов при повторе.
- Юнит-тесты доменной логики события/outbox; интеграционные тесты с Postgres (Testcontainers + Atlas), по паттерну фазы 1.
- «Публикация» на этом шаге может завершаться **заглушкой**: запись в outbox + пометка статуса, либо логирование payload без выхода во внешний HTTP/шину событий — см. раздел ниже. Реальная фоновая обработка очереди — в [`015`](../015-phase-3-asynq-infra-ping-domain-task/) на **Asynq**.

## Не входит в объём
- Введение отдельного классического брокера сообщений (Kafka/Rabbit и т.п.) как стандарта репозитория; замена **Redis + Asynq** на другой движок фоновых задач без ADR.
- Идемпотентность **потребителей** внешних систем (это ответственность интеграций; в задаче — контракт и сторона Profile).
- Фоновый воркер Asynq (следующая подзадача [`015`](../015-phase-3-asynq-infra-ping-domain-task/)).

## Заглушки и внешние зависимости
- **Доставка наружу (внешние потребители):** до готовности контрактов с другими сервисами — outbox остаётся источником истины; интерфейс `Publisher` (или эквивалент) может быть no-op / stdout / тестовая реализация. Передача работы в фон — через **Asynq** ([`015`](../015-phase-3-asynq-infra-ping-domain-task/)), не через отдельный Kafka/Rabbit в рамках принятой архитектуры.
- **Keycloak / AprilHub:** не требуются для ядра outbox, если интеграционные тесты используют тот же подход, что и [`009-phase-1-integration-tests-db-redis`](../009-phase-1-integration-tests-db-redis/).

## Технические ограничения
- Стек: Go, PostgreSQL, Atlas для миграций; Redis/Asynq подключаются в [`015`](../015-phase-3-asynq-infra-ping-domain-task/), здесь — только подготовка данных и контрактов.
- `tenant_id` только из доверенного контекста (как в фазе 1–2); события не утекают между тенантами.
- Секреты только через env / `.env.example`; значения не коммитить.
- При изменении публичного API или добавлении наблюдаемых эндпоинтов — синхронизация `openapi/openapi.yaml` в том же изменении, если это принято в репо.
