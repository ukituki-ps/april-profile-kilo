# 006 — `/healthz`, `/readyz` и синхронизация OpenAPI

## Что это вообще и зачем

Если совсем на пальцах:

- `healthz` отвечает на вопрос: **"процесс сервиса вообще живой?"**
- `readyz` отвечает на вопрос: **"сервис уже готов принимать рабочий трафик?"**

Это важно для инфраструктуры (Docker/Kubernetes/Nginx, деплой-пайплайн, мониторинг), чтобы:

- не отправлять запросы в "полумёртвый" процесс;
- понимать, когда новый релиз реально поднялся;
- быстро и автоматически находить проблемный инстанс.

## Проблема до задачи

До этой задачи в контракте уже были заготовки `/healthz` и `/readyz`, но в реальном Go-роутере они не были реализованы как отдельные endpoints.

Итог: документация и фактическое поведение могли разъезжаться, а это риск:

- инфраструктура проверяет один путь, а сервис отвечает иначе/не отвечает;
- команда видит одно в OpenAPI, а при `curl` получает другое.

## Что сделали (человеческим языком)

### 1) Добавили два публичных endpoint в backend

В HTTP mux добавлены:

- `GET /healthz`
- `GET /readyz`

Оба endpoint **без JWT-авторизации**, чтобы оркестратор/балансировщик мог проверять их всегда, даже без пользовательского токена.

### 2) Зафиксировали понятные ответы

- `/healthz` -> `200 {"status":"ok"}`
- `/readyz` -> `200 {"status":"ready"}`

Важно: здесь нет секретов, нет внутренних деталей БД и т.д.

### 3) Честно обозначили временное ограничение readiness

На этом шаге `readyz` пока упрощённый: он не ходит в PostgreSQL/Redis.

Это сделано специально, потому что полноценная проверка зависимостей запланирована отдельной задачей 008.

### 4) Синхронизировали OpenAPI с кодом

В `openapi/openapi.yaml`:

- добавлено явное описание текущего "упрощённого" поведения `readyz`;
- добавлена схема JSON-ответа для `200` по `readyz`;
- сохранён `503` как целевой сценарий "не готов", который включится после реализации dependency checks в задаче 008.

### 5) Добавили тест, чтобы не сломать поведение в будущем

Тест проверяет, что:

- `/healthz` и `/readyz` доступны без токена;
- оба возвращают `200`;
- тело ответа соответствует ожидаемому `status`.

## Что это даёт проекту прямо сейчас

- Появились стабильные точки health-check для локалки, CI и dev.
- OpenAPI перестал быть "теорией" — теперь он совпадает с фактическими ручками.
- Следующая задача (008) может безопасно углубить `readyz`, не ломая контрактный каркас.

## Как проверить без чтения кода

### Вариант 1: автоматикой (то, что уже прогнано)

- `go test ./...`
- `make openapi-lint`
- `make docs-build`

### Вариант 2: руками через curl

После запуска сервиса:

```bash
curl -i http://127.0.0.1:<port>/healthz
curl -i http://127.0.0.1:<port>/readyz
```

Ожидаемо в обоих случаях: HTTP `200`.

## Границы текущего шага (чтобы не было ложных ожиданий)

- `readyz` пока **не** проверяет реальную доступность PostgreSQL/Redis;
- поэтому в текущем инкременте он всегда отдаёт `200`;
- ветка `503` в контракте оставлена как target-state на задачу 008.
