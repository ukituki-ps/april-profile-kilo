# Дизайн модуля AprilProfile

> Каноническая копия для правок в корне репозитория: `docs/DESIGN_AprilProfile.md` (при изменениях синхронизируйте оба файла).

**Статус:** актуально для разработки в этом репозитории  
**Связанные документы:** `docs/AGENT_ARCHITECTURE_CONTEXT.md` в репозитории; ADR [0002](/adr/april-profile-scope-and-multitenancy), [0003](/adr/april-profile-data-model-policies)

---

## 1. Назначение

**AprilProfile** — централизованное **версионируемое** хранилище **профилей сущностей** организации. Это не только персонал и оргпозиции: в одной полиморфной модели поддерживаются **любые типы объектов**, нужные экосистеме (клиенты, техника, проекты, договоры и т.д.).

**Ценность для платформы:**

- Единая **точка согласованного снимка** атрибутов на момент времени.
- **Маппинг полей** и **разрешение конфликтов** между внешними источниками — на стороне сервиса, а не каждого потребителя.
- **REST API** и **event-стриминг** для синхронных и асинхронных сценариев (доступы, зарплата, процессы, аналитика).
- **Изоляция** потребителей от хаоса прямых интеграций с разрозненными источниками и форматами.

Кратко: AprilProfile — **универсальные версионируемые профили** сущностей; домены HR и службы безопасности — важные примеры атрибутов, но не исчерпывающее ограничение продукта.

## 2. Границы с экосистемой April

| Сервис | Зона ответственности | Связь с AprilProfile |
|--------|----------------------|----------------------|
| **AprilOrgFlow** | Граф организации: иерархии, матричные и ролевые связи | Profile **не** дублирует граф; хранит **атрибутивный профиль** и ссылки на узлы OrgFlow (`org_node_id`, `position_id` и т.п. по контракту). |
| **Keycloak** | Аутентификация, RBAC на уровне экосистемы | Profile применяет **ABAC по атрибутам** (метки полей, сегменты) поверх токена; не заменяет глобальную модель ролей. |
| **AprilEDC** | Внешние порталы (вакансии, резюме и др.) | Только **whitelist** типов и полей; произвольное создание типов из коннектора запрещено. |
| **AprilNFlow** | Уведомления по каналам | Подписывается на события/вызовы по согласованным контрактам. |
| **AprilReport** | Витрины и отчёты | Читает через API или согласованные копии; тяжёлая аналитика не должна ломать OLTP Profile. |
| **AprilFile (File Service)** | Хранение бинарных файлов, presigned upload/download, lifecycle и файловые политики | Profile хранит только ссылки и метаданные файлов в документе; бинарные объекты и их жизненный цикл находятся вне AprilProfile. |

## 3. Мультитенантность

Инсталляция обслуживает **несколько организаций** (`tenant_id` — имя зафиксировать в схеме БД и API).

- Каждая сущность, версия профиля, маппинг внешнего ключа и событие принадлежат ровно одному **`tenant_id`**.
- **`entity_id`** (UUID) — стабильный идентификатор профиля в рамках инсталляции; глобальная уникальность в сочетании с фильтрацией по tenant.
- Уникальность внешних ключей: **`(tenant_id, source_system, external_id)`** (и аналогичные составные ключи по домену).
- **API:** `tenant_id` из **доверенного контекста** (claim Keycloak, заголовок от BFF/gateway), не из произвольного поля тела запроса.
- **Кросс-тенант** по умолчанию запрещён; сценарии «группа компаний» — отдельное решение и модель.

Подробнее — ADR-0002.

## 4. Модель данных (логическая)

### 4.1 Профиль и тип сущности

- **Профиль** — согласованный снимок атрибутов сущности; хранится как документ по **схеме типа** (например JSONB в PostgreSQL).
- **Тип сущности** — запись в каталоге типов с **версионируемой схемой** (например JSON Schema): поля, типы, обязательность.
- Доменные данные разнесены по **namespace** (`hr`, `security`, `finance`, `custom`), чтобы различать authority, валидацию и доступ.

**Целевая детализация (метамодель типа):** семейство логического типа (`namespace` + `code` per tenant) имеет линию **неизменяемых опубликованных ревизий схемы** (`revision_no`); каждая **`entity`** привязана к конкретной опубликованной ревизии; переезд на более новую ревизию — **явная операция** с контролем совместимости документа профиля. Подробно — **ADR-0005** · `docs/adr/0005-entity-type-revisions-and-entity-binding.md`; админский UI — `docs/widgets/profile/entity-types-widget.md`.

### 4.2 Идентичность и внешние системы

- Внутренний **`entity_id`** не меняется после выдачи.
- Соответствия внешним системам — в таблице **`(tenant_id, source_system, external_id) → entity_id`**.
- Слияние дубликатов — **явная операция** с аудитом, не скрытый автоматический merge без правил.

### 4.3 Версионирование и аудит

- Версии профиля — **append-only**: новая версия на каждое применённое изменение; монотонный **`version`** per `entity_id`.
- **Откат** — только как **новая версия**, воспроизводящая выбранное прошлое состояние; история не затирается.
- Чтение «состояние на момент T» — по явному правилу (например последняя версия с `effective_at ≤ T`); при необходимости — отдельное поле **бизнес-даты** вступления в силу.

### 4.4 Источники правды и конфликты

- Разрешение — **по полю или по namespace**, не «один источник на весь профиль».
- Для каждого атрибута задаётся **authority**; итог **детерминирован** опубликованными правилами (приоритет, last authoritative write, ручное разрешение → пометка `manual`).

### 4.5 События

- Минимум в событии: `tenant_id`, `entity_id`, `entity_type`, `profile_version`, `occurred_at`, уникальный **`event_id`** (идемпотентность при at-least-once доставке).
- Упорядочивание по сущности — по **`profile_version`**.

Подробнее — ADR-0003.

## 5. Безопасность и чувствительные данные

- Метки полей (`PII`, `SECURITY`, …) и политики выдачи по ролям/claims.
- Сегмент `security` и аналоги — не отдаются без права (не только скрытие в UI).
- Удаление персональных данных: **псевдонимизация** и ограничение выдачи при сохранении требований к аудиту; полное стирание истории — исключение по процедуре (юридическое согласование).

---

## 6. Интеграции и синхронизация

- Адаптеры к HRIS, AD, CRM и др. — по мере подключения; **батчи идемпотентны**, checkpoint прогонов.
- **AprilEDC:** только разрешённые типы и поля; остальное — staging/inbox, не мастер-профиль.
- **AprilFile:** загрузка/выгрузка и хранение файлов — через отдельный сервис; в профиле фиксируются file-reference данные (`file_id`, тип, размер, checksum, роль файла), а не бинарный payload.

---

## 7. Поиск и аналитика (v1)

- **PostgreSQL:** индексы на ключевые поля метамодели, при необходимости GIN по стабильным путям JSON.
- Отдельный поисковый кластер — при появлении требований; до этого отчёты через **AprilReport** по контракту.

---

## 8. Наблюдаемость

- Метрики: лаг синка по источнику, ошибки адаптеров, очередь Asynq, размер батчей.
- SLO уточняются после нагрузочных тестов; алерты на аномалии (лаг, error rate).

---

## 9. Реализация в репозитории

- **Backend:** Go, модульный монолит, REST, OpenAPI — `openapi/openapi.yaml` в корне репозитория (эволюция по мере реализации).
- **БД:** PostgreSQL 17; **очередь:** Redis + Asynq для фоновой синхронизации.
- **События:** контракт топиков и схемы событий — в том же изменении, что реализация, или по процессу команды.

Структура каталогов кода и модулей уточняется по мере появления реализации; этот документ задаёт **продуктовые и архитектурные инварианты**, а не имена пакетов Go.
