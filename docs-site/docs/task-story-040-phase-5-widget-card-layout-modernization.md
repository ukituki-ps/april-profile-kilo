# 040 — `widget-card`: новый master-detail формат 25/75

## Какая была проблема

Виджет профилей был собран как единый список с inline-формами. Из-за этого сценарий "выбрал профиль слева -> посмотрел/изменил справа" работал хуже, а создание нового профиля перегружало основной экран.

## Что сделали

- Перестроили `ProfilesListWidget` в формат `widget-card` с двухколоночным layout:
  - слева `Card List Column` (25%);
  - справа карточка выбранного профиля (75%).
- В левой колонке оставили и структурировали поиск, фильтр по типу и пагинацию.
- Добавили явный выбор активного профиля: клик по карточке в левой колонке загружает детали справа.
- Перенесли создание профиля в модальное окно, которое открывается кнопкой `+`.
- Справа реализовали режимы:
  - просмотр JSON карточки профиля;
  - редактирование и сохранение через API.
- Сохранили безопасную обработку ошибок API (`401/403/409`) и обновили RTL/MSW тесты под новый UX-поток.

## Что это даёт команде

- Интерфейс ближе к рабочему сценарию операторов: список и карточка больше не конкурируют за место.
- Проще масштабировать функциональность карточки профиля без усложнения списка.
- Создание вынесено в отдельный фокусный шаг, что снижает визуальный шум.

## Как проверить без чтения кода

1. Выполнить `cd frontend && npm run lint && npm run test && npm run build`.
2. Запустить `cd frontend && npm run dev`, открыть `/profiles-list-widget-demo`.
3. Проверить:
   - поиск/фильтр/пагинацию в левой колонке;
   - выбор профиля и загрузку карточки справа;
   - edit/save в правой карточке;
   - создание профиля через кнопку `+` и модальное окно.

## Границы и follow-up

- Backend/OpenAPI контракты в этой задаче не менялись.
- RBAC/tenant-модель не переносилась на клиент и остаётся в серверном контуре.
- Отдельный list endpoint не добавлялся: виджет по-прежнему работает по входному набору `entityIds`.
