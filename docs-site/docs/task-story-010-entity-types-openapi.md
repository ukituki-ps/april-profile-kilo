# 010 — Каталог типов сущностей (draft/published) и OpenAPI-контракт

## Что поменялось

В этом шаге появился первый рабочий слой доменного API для метамодели:

- добавлен каталог типов сущностей с tenant-изоляцией (`/v1/entity-types`);
- реализовано создание черновика типа (`POST /v1/entity-types`);
- реализована публикация типа (`POST /v1/entity-types/{entityTypeID}/publish`) с переходом `draft -> published`;
- добавлена структурная валидация схемы при публикации (тип `object`, непустые `properties`, корректный `required`);
- добавлена Atlas-миграция для полей жизненного цикла публикации в `entity_types`;
- OpenAPI синхронизирован: новые endpoints, схемы запросов/ответов и коды ошибок (`404/409/422`).

## Зачем это команде

- Дальнейший CRUD профилей может опираться на стабильный идентификатор типа и статус публикации схемы.
- Сервис теперь явно разделяет "черновик" и "опубликованную" схему, что снижает риск случайных breaking-изменений.
- Контракт уже документирован в OpenAPI, значит интеграции можно начинать до полной реализации следующих фаз.

## Границы задачи

Сделано в рамках 010:

- базовый API каталога типов;
- хранение опубликованного snapshot схемы и момента публикации;
- предсказуемая обработка повторной публикации и невалидной схемы.

Осознанно оставлено на follow-up:

- CRUD и append-only версии профиля (задача 011);
- authority/merge и конфликты (задача 012);
- ABAC-фильтрация полей в выдаче (задача 013).

## Как проверить без чтения кода

```bash
go test ./...
go vet ./...
make openapi-lint
scripts/check-openapi-compat.sh
make docs-build
```

Что считать успехом:

1. `go test ./...` проходит, включая тесты HTTP-слоя с обработкой ошибок publish.
2. `make openapi-lint` валидирует обновлённый контракт с endpoints каталога.
3. При ручной проверке publish:
   - валидный draft публикуется;
   - повторная публикация даёт `409`;
   - невалидная схема на publish даёт `422`.
