# 031 — `ConflictQueueWidget`: очередь конфликтов authority и merge дубликатов

## Какая была проблема

Backend фазы 2 уже умеет ставить конфликты authority в очередь, разрешать их вручную и объединять дубликаты профилей с аудитом, но в `@april/profile-ui` не было операторского UI: разбирать очередь приходилось только через API.

## Что сделали

- Добавили `ConflictQueueWidget`: список конфликтов с фильтром по статусу и поиском по полям строки.
- Показали детали выбранного конфликта (значения existing/incoming, источники, причина).
- Реализовали **Resolve** через модальное подтверждение и тело `ResolveProfileConflictRequest` (значение + опциональные заметки).
- Реализовали **Merge duplicates** отдельной кнопкой (source/target UUID) с явным предупреждением о необратимости.
- После успеха показываем краткий **аудитный срез**: для resolve — `entity_id` и новая `version` из `ProfileSnapshot`; для merge — целевая сущность и версия из ответа API.
- Ошибки `401/403/404/409` нормализованы в понятный текст; при наличии в теле ошибки выводим `request_id` для корреляции с логами.
- Добавили demo-маршрут `/conflict-queue-widget-demo` и Vitest/RTL + MSW на загрузку, фильтр, resolve и `409` на merge.

## Что это даёт команде

- Оператор видит очередь конфликтов и может закрыть кейс без ручного вызова curl: меньше ошибок и быстрее расследования.
- Роли Keycloak остаются единственным источником права на админ-эндпоинты: UI не обходит проверки, а объясняет отказ.
- ABAC по-прежнему применяется на сервере при чтении профилей; этот виджет работает с **admin**-маршрутами разрешения конфликтов и merge, как в OpenAPI.

## Как проверить без чтения кода

1. `cd frontend && npm run lint -w @april/profile-ui && npm run test -w @april/profile-ui && npm run build -w @april/profile-ui`.
2. `cd frontend && npm run dev`, открыть `/conflict-queue-widget-demo`.
3. Задать `VITE_PROFILE_API_BASE_URL`, `VITE_PROFILE_ACCESS_TOKEN` с токеном, у которого есть tenant claim и realm-роль админа профиля (как на стенде).
4. Проверить: загрузка списка, фильтры, выбор строки, resolve с подтверждением, merge с подтверждением и сообщение при `409`.

## Границы (что не делали)

- Не встраивали виджет в AprilHub и не писали e2e в контуре Hub (задача `032`).
- Не меняли бизнес-правила authority/merge на backend.
- Не добавляли отдельный «id операции» сверх того, что уже отдаёт API (`request_id` в ошибках, версия/сущность в успешных ответах).

## Роли и почему это важно

- Доступ к `GET/POST /v1/admin/profile-conflicts` и `POST /v1/admin/entities/merge` завязан на **realm-роль** (имя из `KEYCLOAK_ADMIN_REALM_ROLE`, по умолчанию ожидается `april-profile-admin`) и валидный JWT с **tenant claim**.
- Если выдать эти права шире политики компании, любой носитель токена сможет вручную переписывать данные и сливать сущности; поэтому роль должна оставаться узкой операционной/админской, а UI лишь отражает отказ сервера (`403`), не пытаясь «обойти» его.
